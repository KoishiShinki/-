# 从旧项目迁移

本指南说明如何将旧项目中的世界线业务数据迁移到 Chronicle Studio。迁移过程应在本地或受控环境中执行，数据库备份、旧源码、上传文件、迁移计划和凭据均应保存在发行目录之外。首次执行前，请在可丢弃的数据库副本上演练完整流程。

## 迁移范围

迁移包括世界线业务表、账号和相关媒体引用。若依仅作为旧系统的迁移背景；不迁移其通用管理模块、菜单路由、权限配置、Redis 会话缓存或旧登录会话。新应用使用独立账号和会话表。

迁移保留 `tl_*` 业务记录的编号和字段语义。旧账号的 BCrypt 密码哈希可以直接迁移，无需导出明文密码；迁移脚本将所有旧账号设置为普通用户。管理员身份需由维护者在目标环境中单独指定。旧会话不会迁移，用户需重新登录。

头像、封面、截图和插图的 `/profile/...` 相对地址可保留。迁移脚本会根据账号和业务引用将这些地址登记到 `app_media` 并重建可确定的所有权。文件本身需复制到新应用的 `STORAGE_ROOT`，并保持相对目录结构。若同一路径被多个用户引用，脚本会停止，需先在备份副本中确认共享文件的归属处理方式。

## 迁移步骤

1. 备份旧数据库和旧文件存储目录，并确认备份可读取。备份不得放入公开发行目录。
2. 创建空的目标数据库，使用 `utf8mb4` 字符集和 `utf8mb4_0900_as_cs` 排序规则，以保留用户名大小写语义。运行新后端初始化结构后停止应用；此时不要注册账号或配置引导管理员。
3. 从项目根目录生成本地迁移计划：

   ```sh
   python scripts/generate_migration.py --source-db legacy_chronicle --target-db chronicle --output ../private-migration.sql
   ```

   将示例数据库名替换为实际名称。该命令只生成 SQL，不连接数据库，也不读取业务数据。输出文件必须位于发行目录之外。
4. 确认源库包含脚本要求的 12 张 `tl_*` 表，且列结构与当前目标结构兼容。迁移语句根据目标结构生成；缺少字段时数据库会报错，不能跳过错误继续导入。需要时先在备份副本中完成结构调整。
5. 使用本地 MySQL 客户端执行计划。目标库中的账号、会话、媒体目录及业务表必须为空；复制过程使用事务，失败时回滚。若媒体引用没有对应账号，或同一地址对应多个所有者，脚本会终止。请在备份副本中核实并修正这些引用后再生成计划。若上次失败留下 `chronicle_migrate_legacy` 存储过程，需在目标库中检查并处理后再执行；不要对原始数据库运行清理操作。
6. 核对账号编号、用户名及业务资源编号。需要管理员时，可将选定账号的 `role` 设置为 `ADMIN`，也可在目标数据库中尚无该用户名时，通过 `ADMIN_USERNAME` 和 `ADMIN_PASSWORD` 配置引导管理员。
7. 将旧文件存储目录复制到新 `STORAGE_ROOT`，保持相对目录结构。在备份副本中修复指向本机绝对路径或已失效外部地址的图片记录。
8. 保持 AI 关闭，启动新应用并检查记录数量、账号登录、公开与私有访问边界、章节导出、图片读取和管理操作。确认基础数据后，再配置新密钥并验证 AI 提供方。

## 验收要点

- 私有世界线不应出现在公开列表，未发布章节不应被公开读取。
- 对照迁移前后的世界线、截图、事件、阶段、国家状态、人物、章节、插图和任务记录数量。
- 普通账号只能访问自己的创作资料，管理员可以执行业务管理操作。
- 图片应从本地存储继续提供，无需将上传文件提交到代码仓库。

迁移脚本要求目标库为空，因此原库与目标库应使用不同数据库。若部署需要沿用某个数据库名称，应先在独立目标库完成迁移和比对，再制定经过演练的切换步骤。涉及触发器、视图或跨库外键时，应单独验证切换影响。确认新应用运行正常后，按组织的数据保留策略处理旧库；始终在发行目录之外保留所需备份。
