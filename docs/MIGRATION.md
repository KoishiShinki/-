# 从旧项目迁移

本项目已完成源码原地替换与本地数据库迁移验收。以下步骤供其他部署复用；实际凭据、旧源码、数据库备份和上传文件均不属于公开仓库。迁移前请先在临时数据库中验证，并保留源码目录外的私有备份。

## 保留范围

保留世界线、AI 叙事及其业务管理后台。根据确认的范围，不迁移若依通用管理模块；新应用提供业务需要的独立账号及管理员角色。

业务数据保持 `tl_*` 表的编号与字段语义，独立账户使用 `app_user`，会话使用 `app_session`。旧账号头像、个人资料头像和封面、上传截图及生成插图保留 `/profile/...` 相对地址；迁移脚本会把这些路径登记到 `app_media` 并保留可确定的所有者。新应用以 `STORAGE_ROOT` 指定私有存储目录，按资源可见性提供读取；同一路径若对应多个用户，迁移会停止，需先在本地备份中核实共享文件的处理方式。

旧用户的 BCrypt 密码哈希可以迁移，不需要导出明文密码。迁移脚本将旧账号统一设为普通用户，是否赋予管理员身份由维护者在本地明确决定。旧会话不迁移，用户需要重新登录。

## 本地迁移步骤

1. 在本地备份旧数据库及旧文件存储目录。备份不得放入待开源目录。
2. 创建空的新数据库时，使用 `utf8mb4` 字符集和 `utf8mb4_0900_as_cs` 排序规则。旧用户名按大小写区分；目标库使用相同语义可避免大小写不同的账号发生唯一键冲突或身份匹配改变。运行新后端一次以初始化 `schema.sql`。此时不要配置引导管理员，不要注册用户；随后停止新旧应用。
3. 生成仅包含迁移语句的本地计划，例如：

   ```sh
   python scripts/generate_migration.py --source-db legacy_chronicle --target-db chronicle --output ../private-migration.sql
   ```

   这个命令不连接数据库、不读取业务数据。请用实际的本地数据库名称替换示例。生成文件不能放在源码发布目录中。

4. 核对旧数据库包含全部 12 张 `tl_*` 表，字段与新结构兼容。迁移语句来自当前目标结构，遇到缺字段会失败，不能跳过错误继续导入。必要时先对旧库备份做结构升级。
5. 使用自己的 MySQL 客户端在本地执行计划。脚本要求目标身份表、媒体目录表和业务表均为空，并在事务中复制数据；失败时回滚。它会从账号头像和业务引用重建媒体归属；`create_by` 为空、账号不存在或资料的 `user_id` 无法对应时会停止，不会静默丢弃媒体归属。同一路径若指向多个用户也会停止。请先在本地备份中核实和修复这些引用。重新执行前需先处理上次遗留的 `chronicle_migrate_legacy` 存储过程，勿对原库执行清理操作。
6. 保留用户编号、用户名和业务资源编号。需要管理员时，在目标库中将明确选定账户的 `role` 设置为 `ADMIN`，或配置一个尚不存在的 `ADMIN_USERNAME` 与 `ADMIN_PASSWORD` 创建独立管理员。
7. 将旧文件存储目录内容复制到新 `STORAGE_ROOT`，保持相对目录结构。旧记录中指向本机绝对地址或失效第三方链接的图片需要在本地修复。
8. 以 AI 关闭状态启动新应用，核对数据量、账号登录、公开/私有边界、章节导出、图片读取和管理操作，再使用新密钥验证 AI 提供方。

## 核对重点

- 私有世界线不应出现在公开列表；未发布章节不应公开读取。
- 迁移前后的世界线、截图、事件、阶段、国家状态、人物、章节、插图和任务数量应一致。
- 普通账号只能访问自己的创作资料；管理员能管理业务内容。
- 旧上传图片由本地文件继续提供，不需要上传到 GitHub。
- 不迁移旧 JWT、Redis 登录缓存、Druid 控制台、若依菜单路由和框架权限配置。

这份迁移计划不携带实际数据。已经验证过备份还原、业务数据逐行校验、账号映射和媒体归属。需要沿用原数据库名称时，先在独立临时库完成迁移和比对，再于维护窗口使用 MySQL 的一次原子 `RENAME TABLE` 切换旧表与新表；涉及触发器或跨库外键的部署需先单独验证。运行新应用验收后再删除临时旧表库，磁盘备份继续保存在公开源码目录外。
